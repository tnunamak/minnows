## Summary

The certification gate — the automated test run that must pass before a change to PDPP (the Personal Data Polyfill Project) can merge — runs its largest test suite two files at a time, no matter how many CPU cores the machine has. On a 24-core machine, that suite alone took roughly 11 minutes even though the machine had headroom to run far more files in parallel; on a busier or slower CI runner it could take even longer, which slows down every contributor waiting on the gate to know if their change is safe to merge.

This PR changes one constant in `reference-implementation/scripts/run-tests.ts` — the script the gate uses to run this suite ("reference-implementation" is this repo's implementation of the PDPP protocol, as opposed to its written spec; "ri-default", the suite name used later in this description, is that same reference implementation's default test suite). The old code capped file-level parallelism (called "file concurrency" in the code) at `Math.min(2, availableParallelism(), testFiles.length)` — `availableParallelism()` is a Node.js built-in that returns the number of CPU cores the operating system exposes to the process, and `testFiles.length` is simply the number of test files selected for this run — meaning "run at most 2 test files at once, or fewer if the machine has fewer cores, or fewer still if there are fewer files than that." The `2` is now `8`. Nothing else about which tests run, what they assert, or how they're isolated from each other changes.

This is safe to raise because of how the runner was already built: each of the parallel "workers" runs one test file in its own child process (its own separate operating-system program, with its own memory, unable to interfere with any other worker's memory), pulling the next file off a shared queue as soon as it finishes one. When a file needs its own database for a test, that database's name is generated from a random ID plus a counter, so two files running at the same time can never collide on the same database name. Raising the worker count from 2 to 8 doesn't change any of that — it just lets more of those already-isolated child processes run concurrently instead of queueing.

8 was chosen empirically, not by a formula, on this session's 24-core development machine (which was itself running other work at the time, using roughly half its cores) — it gave a clear speed win without a systematic search across other values like 4, 6, or 12. A hardcoded cap (rather than always matching the host's full core count) also keeps worst-case resource use bounded on a smaller CI runner with fewer cores.

## Evidence

"Equivalence" here means: run the exact same test suite, at the same commit, once with the old concurrency setting and once with the new one, and confirm the two runs produced identical results — not just "both passed," but the same list of tests run and the same pass/fail/skip counts. This matters because a gate change that quietly changes which tests run, or lets some tests interfere with each other under more parallelism, would be far worse than a slow gate — it would give false confidence.

The original measurement (recorded in this session's history) ran `scripts/test-accounting/authority.ts` — the gate's own certification script, which records exactly which test files ran and their pass/fail/skip counts into a signed "receipt," and which the gate treats as the source of truth for whether a run is valid — twice against the same commit: once with the old cap of 2, once with the new cap of 8. Both runs reported the same commit hash, 10,240 assertions, 9,887 passed, 0 failed, 353 skipped, and 1,031 of 1,031 planned files completed. Both runs also reported the same `manifest_sha256` value — a hash of `test-accounting.manifest.json`, the file listing every test suite the gate knows about and how to run it — confirming both runs read the identical suite configuration and weren't silently working from two different definitions of what "the gate" even runs. The dominant suite, `ri-default` (short for "reference implementation, default"), can run in more than one "profile" — a named execution mode that determines what backs its tests' data storage. `ri-default/memory-default`, the profile measured here, runs entirely in-memory; a separate `ri-default`/PostgreSQL profile (discussed below, under "What was NOT measured") runs the same tests against a real database instead. `ri-default/memory-default` dropped from 649.5s to 224.8s (a 65.3% reduction); the full gate — 16 suites total, as listed in `test-accounting.manifest.json`, the file named above — went from 1,202s to 899s (a 25.2% reduction) — smaller because most of that time is now spent in other suites this change doesn't touch, including `polyfill-connectors` (discussed under "Next bottleneck" below), which already caps its own internal concurrency independently.

I independently reproduced this before opening the PR, rather than relying on the recorded numbers alone: I built a separate clone of this commit, ran that same `ri-default/memory-default` suite once with the cap reverted to 2 and once as committed (cap 8), on a machine that was under heavier concurrent load than the original measurement. My results: cap=2 took 1,079s wall time, cap=8 took 431s (a 60.1% reduction — slightly different from the original 65.3% because of the different host load, but the same direction and magnitude). Both runs' receipts matched exactly: 10,240 assertions, 9,887 passed, 0 failed, 353 skipped, 1,031/1,031 files completed, and an identical `manifest_sha256` (`f1645c5c45a19140...`) between the two runs — the same suite-configuration check described above, independently confirmed.

## What was NOT measured

- **The `ri-default`/PostgreSQL profile** (defined above, under "Evidence") was not re-measured under the new cap, in either the original session or my reproduction. A shared test-database container was in concurrent use by another engineering session at the time, which made a clean before/after comparison impractical. Reading the per-file database-naming code suggests raising the cap here should be safe by the same reasoning given above (each file still gets a collision-proof, randomly-named database) — but that has not been directly measured under this change, and this PR does not alter that profile's code path, only the shared default it now also inherits.
- **Other host configurations.** Both the original measurement and my reproduction ran on 24-core development machines under real background load from other work — not on the actual CI runner this gate executes on in production, which may have a different core count or contention pattern. Anyone running this suite can already set the `PDPP_TEST_CONCURRENCY` environment variable to force a specific worker count instead of using this default of 8 — that override is unchanged by this PR; only the number used when nobody sets it changes.
- **A systematic search for the best cap value.** 8 was tested once and compared only against the current default of 2; values like 4, 6, 12, or 16 were not tried, so this PR does not claim 8 is optimal, only that it is a clear, correctness-preserving improvement over 2.

## Next bottleneck

With this change, the largest remaining contributor to gate time is `polyfill-connectors` (roughly 450s in both the original measurement and, similarly, in my reproduction) — the suite covering this repo's "polyfill" connectors, the ones that read data from a source (an email inbox, a chat export, etc.) without that source offering a real API. It isn't sped up by this change because it already caps its own internal test concurrency independently, inside its own separate invocation of Node's test runner, rather than going through the `run-tests.ts` cap this PR changes. Speeding up the gate further would mean raising that suite's own internal cap next, not this one.
