Someone signs the PDPP Principles, gets a confirmation email, clicks the link, and their name never reaches the register: the private GitHub repository, one JSON file per signatory, recording who has signed. Nobody finds out, because the signer sees a normal page and no maintainer is watching. That journey crosses four systems no unit test can join up: a route handler, a store holding the unconfirmed submission, a mail provider, and the write to that repository. Each is mocked in isolation, and mocks share the assumptions of the code calling them.

This adds `scripts/signing-journey-oracle.mjs`, which judges pass or fail itself rather than replaying steps. Given a base URL, it walks the journey as a supporter does and asserts what each step returns: submit, and expect a redirect whose query string says `signed=pending`; poll a mailbox for the confirmation; confirm, and expect `signed=confirmed`; check GitHub received an "Add signatory" commit — each signature is recorded as one commit — whose stored record matches what was sent; reuse that link and expect `signed=invalid`, proving it single-use; then withdraw, requiring the commits that delete and log it. It writes a JSON receipt and exits non-zero on failure, so a failed run shows how far it got.

Running it surfaced a real defect: a submission omitting `consent_updates`, the optional mailing-list checkbox, is rejected with an opaque 400, because that field requires its key even when unticked. The oracle sends it; the schema is left unchanged.

Verified against a preview: six of six steps passed, and I read the three commits back from GitHub rather than trusting the script. Not run against production. Since withdrawal deletes a real record, the `--keep` flag ends the run after confirming.

## Round 2

An independent review of `signing-journey-oracle.mjs`, the script described above, found that two of its assertions did not prove what they claimed. Both are now fixed.

The withdrawal step could pass on a commit left behind by an earlier run. The oracle confirms a withdrawal happened by looking in the register for a commit with a matching subject line, the first line of a commit message. It searched recent history with no restriction on when the commit was made. Two of the three subjects it looks for contain a random identifier generated for that run, so they could only ever match the run in progress. The third does not: the signing site writes the fixed subject "Record a withdrawal" for every withdrawal by anyone. Any earlier withdrawal still in recent history therefore satisfied that check on the very first attempt, and the step reported success without the current run having logged anything — the exact failure the step exists to detect. Every commit check is now bounded by the timestamp taken when the run starts, which the oracle already computed to filter the mailbox. The bound is applied twice: as a parameter to the request sent to GitHub, so GitHub itself returns only commits in range, and again on each returned commit's own date, so a stale commit cannot slip through if that parameter were ever ignored.

The other correction is to a comment rather than to code, but it would have sent a maintainer to the wrong file. The oracle checks that each commit carries a `Signed-off-by` line, and its header claimed that line comes from a GitHub repository setting requiring sign-off, and that this check was the only thing watching that setting. That is not true: the site adds the line itself, in a function every write to the register passes through, which was merged to `main` in pull request #319 ("write supporter register to staging branch"), after this pull request's branch was created. The check still catches the line going missing, but it is watching code this repository owns, not an external setting. The header now says so, and says plainly that nothing here checks the repository setting. This pull request is rebased onto `main` so the claim matches the code it is asserted against.

Four narrower fixes. Missing configuration exited with a status code found nowhere in the documentation and was the one failure that wrote no receipt, so an automated run could not distinguish a missing environment variable from a crash; it now records a named `setup` failure in the receipt, and exits 1 like every other failure. The oracle compared the email address stored in the register against the raw value of the `SIGNING_TEST_EMAIL` environment variable, but the site lowercases addresses before storing them — so anyone whose address contains a capital letter saw a correct write reported as a broken one. It now lowercases the same way. The path to a signatory's file was assembled from the current date, while the site files each record under the year it was confirmed; those disagree for one second a year, across a UTC new year. The path is now read from the commit that wrote the file, which additionally proves the commit really added a file for this signatory instead of assuming it. Finally, a failed mailbox read wrote the underlying error into the receipt, and that error text contains the full command line: the mailbox reader is supplied by whoever runs the oracle and documented as replaceable, so a reader taking a password as an argument would have written that password to disk. Only the program name and its exit status now reach the receipt.

The receipt also now records the confirm and withdraw links, with the tokens removed — origin, path, and the first eight characters of the token's payload. That is enough to tell one run's link from another's and far too little to rebuild a working token. This was an operational gap: with `--keep`, that entry can only be removed using the link from the email, and the receipt was the natural second copy of it. The tokens themselves stay off disk because they are live single-use credentials.

Two documentation gaps are closed in the oracle's header. The site accepts five submissions per IP address per hour, which matters for a script whose purpose is repeated runs from one machine, and the message shown when that limit is hit now says how long to wait. And the routine that cleans up URLs pulled out of the confirmation email is noted as not safe against lookalike hostnames by itself — what rejects those is the surrounding link extraction, which requires the address of the deployment under test to appear as a literal prefix.

This pull request's first round added twelve offline tests; this round adds sixteen more, and all 28 pass under `node --test`. Each new one was written failing first. The timestamp bound is tested against a commit dated before the run starts and against one dated during it. The path derivation is tested against a record confirmed in one year and read back in the next. The two helpers that strip secrets out of receipt text are tested against a mailbox reader invoked with a password among its arguments, asserting the password appears nowhere in what gets written. Two behaviours these offline tests cannot reach are the timestamp bound working against real commit dates returned by GitHub, and the reworded message shown when the five-per-hour submission limit is hit. I have not re-run the oracle against a live deployment since making these fixes, so neither is confirmed end to end.
