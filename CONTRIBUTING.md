# Contributing to minnows

Maintainer notes: repo layout, packaging rules, how to add a tool or a data pack, and how releases work.
For a new model, a price change or new benchmark data, follow
[docs/playbooks/model-rollout.md](docs/playbooks/model-rollout.md).

## Layout

```
minnows/
├── lib/                       # shared, stdlib-only libraries (dev-time DRY)
├── tools/<name>/              # tool source (CLI ± optional SKILL.md)
├── skills/<name>/             # GENERATED by sync.sh — self-contained shippable skills
├── data/                      # versioned data packs (not CLIs)
│   ├── index.json             #   latest tags + ready-made URLs per pack
│   ├── README.md              #   pack table and conventions
│   └── <pack>/pack.json       #   pack identity + file list
├── scripts/                   # fetch/release/validate packs, render the model-catalog charts
├── sync.sh
└── install.sh                 # skills + bins + data → ~/.local/share/minnows-data
```

## The packaging rule (why `skills/` is generated)

A skill folder gets copied or symlinked **out** of this repo. At that point `from lib import …`
has no repo-root `lib/`, on another machine where you cannot see it.

- **Dev time:** shared `lib/` only when the code is genuinely shared. Tool-private code lives in
  `tools/<name>/lib/`, so unrelated skills do not inherit its state or dependencies.
- **Ship time:** vendored and self-contained. `sync.sh` copies the executable, the shared root `lib/`,
  and that tool's private `lib/` into `skills/<name>/scripts/`. Never symlink `lib/` into a skill.
- Data packs are **read as files** (path or env), not imported like `lib/`. Tools that need a pack
  resolve `$DATA_PACKS_HOME/<pack>` or a pinned tarball.

After editing a tool, `SKILL.md` or `lib/`, run `bash sync.sh` and commit the `skills/` diff. CI fails without it.

## Adding a tool

1. `tools/<name>/<name>` — the CLI (stdlib-only preferred).
2. Optional `tools/<name>/SKILL.md` if agents should auto-discover it. Skills are opt-in: a CLI-only tool costs no skill-index budget.
3. Reuse root `lib/` only when another tool needs the code. Otherwise use `tools/<name>/lib/` with the existing `_load_lib()` bootstrap.
4. `./install.sh`.

MCP is off the table by default for this class of local tool: every tool is a CLI that a person or an agent can run.

## Adding a data pack

1. `data/<pack>/pack.json`, the files, and a `README.md` with a **Get this pack** table (real links).
2. A row in `data/README.md` and an entry in `data/index.json`.
3. `./scripts/release-data-pack.sh <pack> <semver>`, then commit (`--push` when ready).

Before you open a PR:

```bash
uv run --with jsonschema python scripts/validate_data_pack.py --require-jsonschema
python3 scripts/check_freshness.py --max-age-days 45
python3 scripts/render_model_catalog_charts.py --check   # fails if the charts or README block are stale
```

If `--check` fails, run `python3 scripts/render_model_catalog_charts.py --png` and commit the result.

## Releases (CI)

Two tracks run from `main`:

1. **Repo releases** (`vX.Y.Z`): [semantic-release](https://github.com/semantic-release/semantic-release) from conventional commits (`feat:`, `fix:`, …).
2. **Data pack releases** (`data-<pack>-vX.Y.Z`): when `data/<pack>/pack.json` declares a `tag` with no GitHub Release yet, CI publishes the tarball and updates `data/index.json` (`scripts/ci-publish-pending-packs.sh`).

Workflows: `.github/workflows/release.yml` (release + packs) and `.github/workflows/data-packs.yml` (PR validation, freshness, chart check).
Manual pack release: `./scripts/release-data-pack.sh <pack> <semver> [--push]`.

Machines that use the clone install (`./install.sh`, or dotfiles `setup.sh`) get pack files through git pull and symlinks.
Remote consumers use `fetch-data-pack.sh` or the release assets.
